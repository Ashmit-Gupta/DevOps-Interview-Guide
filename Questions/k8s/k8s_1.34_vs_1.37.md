# What is the difference between Kubernetes 1.34 and 1.37?

## Answer

They are **three minor versions apart** (1.34 → 1.35 → 1.36 → 1.37). Kubernetes only supports **one minor version at a time**, so you cannot jump 1.34 → 1.37 in a single upgrade. 1.34 (August 2025, “Of Wind & Will”) is the baseline; 1.37 (August 2026, “Garhwal”) is where several of those features become Stable and a few breaking deprecations land.

### What 1.34 already had

- **DRA core APIs GA** (`resource.k8s.io/v1`) — GPUs/NICs via ResourceClaim / DeviceClass.
- **VolumeAttributesClass GA** — online volume parameter changes via CSI ModifyVolume.
- **Structured AuthenticationConfiguration GA**, selector-based authorization, tighter anonymous-access controls.
- **Streaming list responses**, **resilient watch cache** (feature gate Stable), **ordered namespace deletion**.
- **KYAML** as Alpha (`kubectl get -o kyaml` behind `KUBECTL_KYAML=true`).
- **Pod-level resource requests/limits** still maturing (not fully Stable).
- **cgroup v1** still usable; automatic cgroup driver detection being pushed.

### What changed by 1.37 (the interview-relevant deltas)

| Area | 1.34 | 1.37 |
| --- | --- | --- |
| KYAML | Alpha | **Stable** — `kubectl get -o kyaml` |
| metrics.k8s.io | Long-lived Beta | **Stable v1** (`kubectl top`, HPA) |
| HPA scale-to-zero | Not default | **Beta, on by default** (`minReplicas: 0` with object/external metrics) |
| Watch cache / APF | Resilient init starting | **Fully Stable/locked** — fewer etcd thundering herds; clients must handle **HTTP 429** |
| DRA extras | Core GA | **Device taints/tolerations, extended resources via DRA, ResourceClaim device status** all Stable |
| Node declared features | Earlier | **Stable** — nodes advertise feature support for skew |
| StorageVersionMigration | External migrator | **Built-in, Stable** — rewrite etcd storage versions / encryption |
| Pod certificates + ClusterTrustBundles | Earlier stages | **Stable** — first-class mTLS identity for Pods |
| Gang scheduling / Workload API | Earlier | **Beta** — all-or-nothing PodGroups |
| Memory QoS | Limited | **Beta** on **cgroup v2** (`memory.min` / `low` / `high`) |
| Admission | API-only webhooks | **Beta**: policies from **files on disk** (cannot be deleted via API) |
| kube-proxy IPVS | Supported | **Deprecated** — migrate to **nftables** (iptables still works) |
| kube-dns | Legacy | **Deprecated** — use CoreDNS |
| Static Pods + Secret/ConfigMap refs | Bug allowed it | **Forbidden** (`PreventStaticPodAPIReferences` removed) |
| cgroup v1 | Still common | **Soft-fail since 1.35**; kubelet fails unless you override; **removal coming** |
| APIs removed in 1.37 | Still present in 1.34 | `ClusterTrustBundle` v1alpha1, `IPAddress`/`ServiceCIDR` v1beta1, `VolumeAttributesClass` v1beta1 |

### Practical takeaway

1.37 is not a “new cluster product” — it is **three upgrade hops** of hardening (API server, DRA, identity, storage migration) plus **cleanup** (IPVS, kube-dns, cgroup v1, beta APIs). Before you plan 1.34 → 1.37, inventory: kube-proxy mode, cgroup version on all 40 nodes, CSI/CNI/CRI versions, leftover `v1beta1` objects, and any static Pods that mount Secrets/ConfigMaps.
